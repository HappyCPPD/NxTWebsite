#3. The real surface: /auth/mint

A method-specific route missed by GET fuzzing:

/auth/mint takes the caller's base claims (sub, iat, exp) and merges in attacker-supplied claims, then re-signs a fresh token with the broker key. This is the capability broker "minting" a derived capability token - and it is where the vulnerability lives.

The mint endpoint applies several filters to extra_claims:

  • A. Raw-byte blocklist - rejects if the literal bytes admin, root, superuser, … appear anywhere in the encoded claims: {"error":"extra_claims bytes contain forbidden token \"admin\""}
  • B. Decoded-value blocklist - case-insensitive scan of decoded values: {"error":"extra_claims contain a forbidden role literal"} (caught "ADMIN").
  • C. Semantic role check - a text string role must be "user"; non-string "structured claim objects" are allowed: {"error":"role \"moderator\" is not permitted"} / {"error":"role must be a text string or a structured claim object"}

Capabilities, by contrast, are free: {"caps":["read:vault"]} mints cleanly. The only obstacle is getting role == "admin" past filters A/B/C.

#4. Exploit - two CBOR canonicalization tricks

The title is the hint: canonical CBOR. Two deviations from canonical CBOR each defeat a different filter, and together they smuggle admin through.

#4a. Indefinite-length string to beat the byte scan (A)

The raw bytes now contain adm and in but never the contiguous ASCII admin, so the byte-level blocklist (A) misses it. (A definite string 65 61646d696e is rejected immediately.)

#4b. CBOR tag 55799 to beat the decoded-value scan (B) and the role check (C)

Tag 55799 is the "self-describe CBOR" marker. cbor2 (and most decoders) transparently unwrap it to the bare value on decode:

Wrapping the value in 55799 makes the mint filter treat the claim as a structured object (so the string-role check C is skipped and the value scan B does not see a bare string literal), while the decoder that builds the final token payload unwraps it back to the string 'admin'.

#5. Why it works (root cause)

/auth/mint performs validate-then-reserialize with a decoder/filter pair that disagrees on non-canonical CBOR:

  • The filters inspect raw bytes and/or decoded values under assumptions that hold only for canonical encodings (contiguous string bytes, bare values).
  • The serializer uses a full CBOR decoder that normalizes the item (unwraps tag 55799, concatenates indefinite-length chunks) into a form the downstream vault-api treats as the privileged value.

Any one of the three defences is bypassable individually; combined, the indefinite-length string hides the literal from the byte scan and tag 55799 hides it from the value/type scan. The fix is to canonicalize once, validate the canonical form, and sign exactly that form (RFC 8949 §3.9 / §4.2), and to reject tags and indefinite-length items in a security-sensitive token.
