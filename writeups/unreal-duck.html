Unreal Duck UE5 client, hidden cheat codes

rev
flag SOLARCTF{unr34l_3ng1n3_p4th_f1nd1ng_0n_w1nd0ws}

Author: SD4RK · Task: unreal_duck.zip · Brief: "This game hides something, but what?"

Flag: SOLARCTF{unr34l_3ng1n3_p4th_f1nd1ng_0n_w1nd0ws}

The flag arrives as a handwritten image with the note "all lowercase".

#TL;DR

The zip holds a UE 5.7 Windows client for a multiplayer duck game. The client connects to a live dedicated server. The server sends the flag (an image) to whoever completes the route. The route has three trigger volumes, and the hidden part is that inside each volume you have to type a secret 5‑letter code. The client hashes the letters and the server checks them. I brute-forced the three codes offline from constants in the binary: ILOVE / DUCKS / ALOTT ("I love ducks a lott"). Then I ran the client under Wine on Linux, drove the duck through the route with scripted keypresses, typed the codes and got the payload.

#1. Recon

The zip unpacks to a standard UE 5.7 shipping build:

A full asset dump finds no flag anywhere in the client: no literal, no encoded form, no texture, no text asset. The useful finding is in DefaultGame.ini inside the pak:

UDP 24115 on that host is live. It silently drops query probes, but it doesn't return ICMP unreachable the way closed ports do. The only content sink in the client is the RPC ClientReceivePayload(MessageTitle, ImageBytes), which fills a "Message received" widget. Nothing in the client calls it locally, so the flag has to come from the server.

DefaultEngine.ini also has CoreRedirects that rename the route-record and GameMode properties to Greek gibberish (DuckRouteRecord.N4 → ηψχ and so on). That's obfuscation of the data layout, not a cipher.

#2. The route

The AUnrealDuckGameMode constructor (0x144387770) hardcodes the route as doubles:

field value
volume extents (1000, 1000, 260)
volume 0 / 1 / 2 (−1900, −1900, 540) · (−1900, +1900, 540) · (+1900, +1900, 540)
endpoint (+1900, −1900, 540)

FUN_144389c10 spawns one ASessionVolume per point and gives each a letter code equal to its spawn index (mov byte ptr [rdi+0x2c0], bpl): 0, 1, 2.

The volumes start at z = 280. Standing on the ground (capsule centre z≈92) never touches them. You have to be up on the 200‑high blocks/ledges around the arena edge. A ramp near the SW corner leads onto a perimeter ledge that runs past all four corners.

#4. Running the client on Linux

The previous notes got several things wrong here, so these are the details that mattered:

  • -nullrhi isn't stripped. The string is stored UTF‑16 and an ASCII grep misses it. The client boots under Wine 10 with it. With no window, though, there's no input, so the actual run used -d3d11 (Wine's wined3d) inside a private Xvfb :77. The UI renders, the 3D view is black, and keystrokes can't leak to the real desktop.
  • The connect address is hardcoded. FUN_14437fe50 returns the literal 109.120.147.90:24115 and ignores -ServerAddress=. I patched a copy of the exe (UDRelay-Win64-Shipping.exe) to point at 127.0.0.1:7777, where a Python UDP relay (relay.py) logged everything. That gave me traffic, chat and the kick reasons.
  • -ConnectOnLaunch loops. It re-fires on every BeginPlay, including after joining, so the client reconnects over and over. I clicked Play in the menu with xdotool instead.
  • Low resolution. Software GL is slow. At 1024×640 the client ran at ~1 - 2 FPS and the server rubber-banded the duck. At -ResX=480 -ResY=300 with scalability cvars turned down, it moved at normal speed.
  • Idle kick. The server disconnects you "after 30 seconds without movement" (jumping doesn't count).

#Position feedback

Yama ptrace_scope=1 only allows a process to read its ancestors' children, so the controller (ctl.py) spawns the game as its own child and reads /proc/<pid>/mem:

  • PlayerController = heap object whose vtable is 0x147118aa0
  • PC+0x2f8 → Pawn, Pawn+0x1c0 → RootComponent, Root+0x1f0 → ComponentToWorld (FTransform with padded double vectors: quat | xyz,pad | scale,pad), giving the world position
  • The route state can be read the same way (PC+0x7c8 active code, PC+0x7b8 visited list, PC+0x808 recorded letters, PC+0x7e8 per-code hash diffs)

I tried teleporting by writing the location: the server snapped it back, so movement is server-authoritative and the duck has to actually walk. Movement is relative to the spawn yaw, which changes between spawns. I read it from the pawn's quaternion and mapped W/A/S/D to world axes.

#5. The run

Spawn at (0, 0, 302), yaw 0, so W = +x and D = +y.

  1. Walk to (−700, −1200) on the ground, then hold S (−x) with a few jumps. The duck climbs a ramp onto the west ledge at (−1864, −1516, 292). The visited list becomes [0], so the duck is in volume 0.
  2. Type ilove. The recorded letters read 08 0b 0e 15 04 = I L O V E.
  3. Hold only D (+y) along the ledge to y = 1790. Leaving volume 0 sends the push, and entering volume 1 doesn't record anything because no new key press happens inside it. Visited = [0,1]. Type ducks.
  4. Hold only W (+x) along the north ledge to x = 1818. Visited = [0,1,2]. Type alott.
  5. Hold only A (−y) along the east ledge to the endpoint (1613, −1850). All client-side diffs are 0 and the "route complete" flag at PC+0x7e4 is 1.
