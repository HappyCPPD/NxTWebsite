mirage blind format string, no binary

pwn
flag isfcr{bl1nd_f0rmat_str1ng_h4s_n0_b1n4ry}

#1. Prompt analysis

Description:

"An echo that repeats back a little more than you said." nc 0.cloud.chals.io 23023

The phrase "repeats back a little more than you said" is a textbook description of a printf format-string leak: the service takes your input and hands it straight to printf() as the format string, so %p / %s make it print extra (uninitialised stack, memory at pointers).

No binary was shipped. The flag text itself (bl1nd_f0rmat_str1ng_h4s_n0_b1n4ry) confirms the intent: solve it blind, no checksec, no disassembly.

#2. First contact

Banner is literally just the prompt "> ". Every line is echoed back.

Feeding format specifiers immediately confirms the bug:

0x7025702541414141 is "AAAA%p%p" - our own input buffer, which lives on the stack. The repeating 0x70257025… words are the %p pattern repeating. Conclusion: classic stack-based format string, our buffer starts at argument index 6 (8-byte words).

An 8-byte-aligned sweep (AAAAAAAA.%p.%p...) revealed the memory layout:

The 0x40…/0x48…/0x4b… addresses are not randomised → the binary is a static, non-PIE executable (statically linked glibc - later reads showed buffers flags 0xfbad2887, i.e. _IO_2_1_stdout_, and libc paths like /sysdeps/x86/dl-cacheinfo.h). That means fixed global addresses are readable without any leak.

#3. Building a working arbitrary read

Naively placing the target address first fails:

Reason: p64(0x48725b) = 5b 72 48 00 00 00 00 00. printf reads the buffer as a C string, so it stops at the first 0x00 and never reaches %6$s.

Fix: put the address after the format specifiers. The buffer starts at argument index 6, so a pointer placed at buffer offset OFF is argument index 6 + OFF/8.

Verified against known data:

Arbitrary C-string read confirmed.

#Quirk: leading character is dropped

In the multi-reader we noticed the first byte of the payload never appears in the output - the service effectively calls printf(buf+1) (or otherwise eats the leading char). All argument indices are unaffected (they depend on buffer position, not the format-string start), so we simply don't rely on the first byte.

#Quirk: one line per TCP segment

The server reads with a single read() and only processes the first line of a chunk; extra lines pipelined in the same send() are discarded:

So requests must be sent one line at a time and the prompt awaited.

#4. Speeding up - multi-string read

printf accepts many positional specifiers in one format string, so one request can read many addresses at once. Pointers are parked at buffer offset 256 → argument indices 38, 39, 40, …:

Response is s0|s1|...|s_{n-1}| followed by the padding and raw address bytes. Result: ~30 addresses per round trip, ~15 ms per address - enough to sweep whole memory regions in seconds.

flag.txt is opened by the program at startup - its name sits in the binary's own .rodata:

The file is read into a fixed global buffer in .bss. Sweeping .bss (0x4b5000 - 0x4b7000, stride 8) found it:

Direct re-read of neighbouring addresses (0x4b6ab0/0x4b6ab8 are empty / NUL) pins the string start exactly at 0x4b6ac0:

Write primitives (%n) were never needed - the flag is simply leaked out of a global through the arbitrary read.

#8. Lessons / gotchas

  1. No binary ≠ no solve. Blind format-string work: %p to map the stack, then identify non-randomised addresses to prove static/non-PIE.
  2. NUL bytes kill a format string. Always place binary addresses after the specifiers; the format string is a C string.
  3. Multi-specifier reads (%38$s%39$s...) turn a 1-read-per-RTT into a ~30-read-per-RTT scanner.
  4. Interaction quirks matter: here the server processes exactly one line per TCP segment and appears to drop the leading character of the line.
  5. The flag itself was the hint: bl1nd_f0rmat_str1ng_h4s_n0_b1n4ry.
