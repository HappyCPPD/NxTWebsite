#2. Leaking fragments with strings

strings coughs up four suspicious 8-byte fragments, each ending in a stray H:

Stripping the trailing H (which is really the first byte of the next instruction's opcode being mistaken for text) leaves:

Concatenating gives OWASP{th3_s0ul_sl_st0n3_wh1sp3r} - visibly almost right but with a duplicated sl. That seam is the tell: the pieces are overlapping, and reading them naively is a trap. Time to read the actual code.

#3. main() - the gate

0x6c756f73 is 73 6f 75 6c = soul. The compared constant is built on the stack, not stored as a plain string in .rodata, which is why it doesn't appear as its own entry in strings.

So the "secret phrase" the vault is guarding is literally soul. A match falls through to soul_stone().

#4. soul_stone() - where the flag actually lives

soul_stone() assembles the flag from four 64-bit movabs immediates written to overlapping rbp-relative slots, copies 29 bytes (0x00..0x1C) into a local buffer, NUL-terminates it, then printf("Flag: %s"):

Laying the writes out by rbp offset:

immediates (hex) little-endian ASCII written at
0x68747b505341574f OWASP{th rbp-0x70
0x735f6c7530735f33 3_s0ul_s rbp-0x68
0x5f336e3074735f6c l_st0n3_ rbp-0x63
0x7d72337073316877 wh1sp3r} rbp-0x5b

The third write sits at -0x63, three bytes into the second write's slot. It re-lands l, _, s over the exact same l, _, s that 3_s0ul_s already ends with - a deliberate overlap that reproduces the seam we saw in strings. Same values, so nothing is corrupted; it just exists to make linear/naive reconstruction produce the wrong ...sl... result. Reading from -0x70 upward with later writes winning:

→ OWASP{th3_s0ul_st0n3_wh1sp3r}

#6. Takeaways

  • "Not stripped" is a gift: nm handed over main and soul_stone.
  • A stack-built strcmp constant is a cheap way to hide a password from strings; recognize the mov DWORD PTR [...], imm + strcmp idiom.
  • Overlapping movabs immediates are a classic obfuscation: the fragments in strings look almost right but duplicate a seam character. Trust the disassembly's memory layout, not the string dump.
  • Two independent methods (live run, static decode) agree - high confidence.
