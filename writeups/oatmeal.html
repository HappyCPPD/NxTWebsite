Oatmeal ART OAT is authoritative over the APK

rev
flag isfcr{5958fbb07efd243b}

#Challenge

A device belonging to a person of interest was imaged last week. It was running an in-house vault app called SilverGate. Two files came back from the image. See what you can pull out of them. Attachment: silvergate.apk, base.odex. Flag format: isfcr{...}.

Two artifacts:

  • silvergate.apk - the staging build (com.silvergate.vault, classes.dex, compiler metadata "version":"8.2.2-dev").
  • base.odex - the optimized (real) app code for the device, an ART OAT file (oat\n243, ART-OPT/13.0.0-r43, art.compiler.filter=speed-profile, tag ARM64-A75-v4.3). The odex is the file of interest: it is what actually ran.

The apk's assets/notes.txt is a planted in-fiction artefact that both hints and misleads ("staging flag format … replace before shipping", "SHA256 constant … derived from the lowercased passphrase", two strings isfcr{ / oatmeal labelled "known-benign"). Treat it as narrative, not ground truth.

#Structure of base.odex

The odex names exactly three methods: checkFlag_v1_LEGACY, checkFlag_v2, finalizeFlag.

#The three compiled methods

#checkFlag_v1_LEGACY @0x7e0 - decoy / dead end

Requires input length 0x20 (32) and does a straight memcmp(input, EXPECTED) against the 32-byte SHA-256 constant at 0x1c8. Since EXPECTED is a SHA-256 hash, this path is one-way - deliberately unsolvable. (And sha256("art_image_took_the_cake!") ≠ EXPECTED, confirming EXPECTED belongs to a different, unrecoverable "staging" passphrase named in notes.txt.)

#checkFlag_v2 @0x4b0 - the real checker (a tiny stack-less bytecode VM)

Requires input length 0x18 (24). It walks the bytecode at 0x290, 2 bytes per instruction: op = hi nibble, dst = lo nibble, plus one operand byte.

op handler semantics
1 ldrb w12,[x27,op] r[dst] = input[op]
2 const from T0 r[dst] = T0[op] ^ ((op*0xa7)^0x5c & 0xff)
3 const from T1 r[dst] = T1[op] ^ (((op+0x18)*0xa7)^0x5c & 0xff)
4 const from T2 r[dst] = T2[op] ^ (((op+0x30)*0xa7)^0x5c & 0xff)
5 mov w12,w11 r[dst] = imm(op)
6 add r[dst] = r[dst] + r[op]
7 eor r[dst] = r[dst] ^ r[op]
8 lsl/lsr r[dst] = rol8(r[dst], op & 7)
9 cmp+b.ne fail assert r[dst] == r[op]
a mov w0,#1; ret return true

#finalizeFlag @0x820 - the flag producer

Called with the 24-byte secret. (It also loads x4 = 0x1e8 but never uses it - that address is exactly the "isfcr{%016llx}" string, the author's fingerprint that finalizeFlag's uint64 is formatted by that template.)

#Reproduce

Pure stdlib; parses the tables/program straight out of base.odex.

#Method notes

  • silvergate.apk is the marketing/staging build; the odex is authoritative. A real device runs the compiled odex, and the odex's embedded dex body is encrypted (dex\n035 magic in the clear, body high-entropy) - the real LockActivity lives behind it. The three compiled methods are enough to solve: one dead-end hash check, one invertible VM, one flag finaliser.
  • The planted notes.txt steers you to deriveFlag/EXPECTED (both decoys).
  • ARM64 via capstone; the VM program was decoded by hand from its interpreter.
