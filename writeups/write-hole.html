Write-Hole RAID5 write hole and AEAD recovery

forensics
flag isfcr{p4r1ty_n3v3r_l13s_wr1t3_h0l3_r3m3mb3rs}

#The story

A three-drive NAS lost power partway through writing a sealed report, and nobody had saved the RAID settings. The three drives were pulled and imaged raw. The report holds a custody token for a piece of evidence that cannot be reissued.

We get bay0.img, bay1.img, bay2.img (17 MiB each), and a flag format isfcr{...} (see the caveat at the bottom).

This is a RAID5 write-hole challenge. Every "easy" piece is really a decoy for the one genuinely nasty piece at the end: a record whose GCM tag is the only thing the crash destroyed.

#1. Fingerprinting the images

Each image is pure high-entropy data except for a band of structured, mostly-zero content starting at 0x100000 (1 MiB). Dumping that band immediately leaks the filesystem:

An ext4 primary superblock sits at offset 56 of its 1024-byte header, i.e. at 0x100400. Ext4's primary superblock lives at filesystem offset 1024. Therefore filesystem logical 1024 == raw 0x100400, i.e. logical 0 == raw 0x100000. The drives reserve a 1 MiB metadata area at the front (the high-entropy first MiB on every drive) - classic hardware/md-style layout with the RAID superblocks wiped.

The ext4 superblock only appears on bay0 and bay1 at 0x100400; on bay2 those bytes are zero. Two identical data copies + one zero chunk = XOR parity, so this is RAID5.

#2. RAID5 geometry

We need three unknowns: chunk size C, base offset D, and the parity/data mapping. Cheap brute force with a filesystem-validity nails all of them.

Distinctently: assemble the logical device for every (C, drive order, parity rotation, data order), then run e2fsck -fn on it. Exactly one class of configs comes out clean:

The earlier "XOR of the 3 drives at every offset" heuristic is a red herring here: it only returns 0 in the untouched all-zero stripes, because the interesting stripes are deliberately inconsistent (that is the write hole). Validity of the resulting ext4 is the reliable oracle.

After assembly: 32 MiB logical ext4, Filesystem state: clean (but needs_recovery), 512 inodes, /stage, /etc, /docs, /backup, /var.

#4. payload.bin and the write hole

payload.bin is a 196608-byte file = 6 × 32768 records, and the ext4 extent is (0-47):1160-1207, i.e. logical 0x488000..0x4B8000, contiguous. Mapping that through the RAID5 geometry:

logical chunk record physical (raw offset)
145 rec0 bay2 @ 0x340000
146 rec1 parity: bay2 ^ bay1 @ 0x348000
147 rec2 bay1 @ 0x348000
148 rec3 parity: bay0 ^ bay1 @ 0x350000
149 rec4 bay0 @ 0x350000
150 rec5 parity: bay0 ^ bay2 @ 0x358000

Records 0/2/4 sit intact on single drives. Records 1 and 3 (and 5) are in stripes whose data chunk was never written - bay1@0x348000, bay0@0x350000 etc. still hold the previous night's ciphertext (job 6/job 0). Those are exactly the RAID5 stripes caught mid-write: the data chunk is stale but the parity is the new XOR, so

Recovering rec1 and rec5 this way is routine: bay1^bay2 @ 0x348000 and bay0^bay2 @ 0x358000 both decrypt cleanly with AESGCM.

Rec3 is different. bay0^bay1 @ 0x350000 starts with the correct nonce …0007 00000003 (a 2⁻⁹⁶ coincidence if it were wrong) but the resulting record fails AESGCM.decrypt - i.e. the first 12 bytes of the parity chunk are right and something later is wrong. The write of the parity chunk itself was torn: the tail never landed.

There is no way to tell from the tag-dependent decryption which bytes are good. But AES-GCM is CTR + GHASH:

The keystream depends only on the key and the 12-byte nonce - both of which we already have. So we bypass the tag entirely:

That yields a fully coherent part 4/6, ending in the report's PAD … trailer - proving the ciphertext really was intact and only the tag was lost. (Cross-checked by running the identical CTR routine on record 0 and matching AESGCM output byte-for-byte.)

A stream-cipher record survives losing its authentication tag. That is the crux of write-hole: the crash did not corrupt the message, only its seal.

#Lessons

  • Non-zero entropy everywhere is not "encrypted metadata" - find the one structured band and identify the filesystem by magic (53ef).
  • Use the artifact's own validity (e2fsck -fn, dumpe2fs) as the brute-force oracle for RAID geometry instead of XOR-consistency, which is broken by design in a write-hole challenge.
  • "Burn-after-read" secrets survive in stale blocks when a volume is overwritten in place.
  • For any CTR/AEAD stream construction, a lost authentication tag ≠ lost data. If you hold the key and nonce, you hold the plaintext.
