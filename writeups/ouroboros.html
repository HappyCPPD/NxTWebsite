#1. Triage

mmap + mprotect + memcmp is the classic JIT fingerprint: the program manufactures machine code at runtime, makes it executable, runs it, and then memcmps a buffer. There is no flag string in the binary - nothing to grep.

#2.2 Four JIT blocks (0x4004dc .. 0x400704)

sysconf(_SC_PAGESIZE) sizes an anonymous RWX page (via mmap, prot=3). Then a loop runs four times, rbx = 0..3. Each iteration:

  1. packs input[8*rbx : 8*rbx+8] into a 64-bit word;

  2. computes seed = word ^ state (state starts at 0x1f0d1e5cafeb00b5, r9);

  3. synthesises a function into the mmap page:

    So the generated code is template[b] XOR keystream(seed). The keystream is a splitmix64 stream whose mix inputs are an arithmetic progression seed+2G, seed+3G, …;

  4. guards the code with a splitmix chain hash:

  5. mprotect(page, RX), call page with rdi = rsp+0x40 (the working buffer),

  6. updates state = chain_hash(code, state) - the code feeds the next block's key. Hence Ouroboros: each block eats the previous block's tail. This is the "self-reference" the name points at.

#3. Why the guard looks unbreakable (and isn't)

The guard is a 64-bit preimage: for a random word the chain hash matches E[b] with probability 2⁻⁶⁴, and the unknown word is 64 bits. So there is exactly one word per block, and brute force is 2⁶⁴ per block - infeasible.

The way in is the opposite direction: recover the CODE, not the word. The generated code is a normal compiled C function, and all four functions share the same prologue. Recover the code and the keystream falls out, which gives the word directly.

No search at all. state is carried across blocks exactly as the binary does: state = chain_hash(code, state). Run this for b = 0..3 and the four words spell the flag. Every recovered block's chain hash matches its stored E[b], which is independent proof the recovery is exact.

#4. The four generated programs

Disassembling the recovered code (all share prologue/epilogue and loop i<32) gives a clean four-stage byte transform of the 32-byte buffer B:

b len operation
0 85 B[i] ^= (7*(i-13)) & 0xff
1 93 B[i] = (B[i] + B[(i+1) & 31]) & 0xff (in-place, forward)
2 96 B[i] = rotl8(B[i], 3)
3 85 B[i] ^= (31*i + 0x3c) & 0xff

So the acceptance condition is fully explained: the JIT blocks perform a fixed invertible byte mixing of the input, and the flag is the input whose mixing lands on the stored 32-byte constant.

#5. The flag

Concatenated: isfcr{c0d3_th4t_3ats_1ts_t41l!!} - leetspeak for "code that eats its tail!!" - which is precisely an ouroboros, and exactly what the program does: the generated code's hash seeds the next block's code generator.

#6. Verification (the only oracle that counts)

Two independent confirmations: (a) all four JIT guard hashes match the stored constants, and (b) the original binary prints CORRECT.

#7. Takeaways

  • JIT + mprotect + memcmp is a code-generation challenge, and the generated code almost always has a fixed prologue. That prologue is free known-plaintext against any template XOR keystream scheme. Recover the keystream, and the "key" (seed) - and therefore the input word - falls out with no search.
  • The scary 2⁻⁶⁴ hash guard is defence in the wrong direction: it stops you guessing the word, but the word is derivable from the code, so the guard is never brute-forced at all.
  • Keep the recovered semantics as a second, independent check: replaying the four byte transforms reproduces the .rodata memcmp constant exactly.
