the-press inverting an LZMA-style range coder

rev
flag isfcr{r4ng3_c0d3r_b1t_3x4ct_y0!}

#1. Triage

The prompt: "Hand it 32 bytes. It will tell you nope."

strings gives the tell:

So it reads exactly 0x20 (32) bytes and compares something to a hardcoded blob. The success string is CORRECT; the %d format string for the length error also says the required count is embedded as an immediate (0x20).

objdump -d shows the whole logic inlined in main at 0x4003c0, with a single memcmp call. Crucially the binary imports only fread, memcmp, fprintf, puts - no crypto library. Everything is hand-rolled.

#2. The .rodata target

main does memcmp(0x4030a0, 0x4012e0, 0x24) - i.e. it compares a 36-byte output buffer against this hardcoded 36-byte blob. So the target is:

The leading 0x00 and the trailing 0x00 are a strong hint: this is a range-coder byte stream (the classic LZMA coder emits a leading dummy cache byte of 0 and pads on flush).

#3. Reading the algorithm

The interesting region is 0x400470 - 0x400571. Annotated:

Per bit:

0x400700 is textbook shift_low (LZMA RangeEncoder::ShiftLow):

State layout:

addr meaning init
0x4030e0 pending (LZMA cacheSize) 1
0x4030e8 cache 0
0x4030ec range 0xFFFFFFFF
0x4030f0 low (64-bit) 0
0x403080 output length 0
0x4030a0 output buffer (0x24) -
0x403100 probability table, 65536 × u16 0x0800

0x400420 initialises the whole 0x20000-byte probability table to 0x0800 (half of the model total 0x1000, i.e. p = 1/2), confirming the model.

At 0x400558 the program calls shift_low five times in a row - the standard LZMA flush. Then it checks out_len == 0x24 and memcmps against the target.

Conclusion: chall is a range ENCODER. It reads 32 bytes, XOR-diffs them (D[0]=M[0], D[i]=M[i]^M[i-1]), encodes the 32 diff-bytes with an order-1 byte-context binary-tree model, and compares the 36-byte coded stream to the hardcoded target. We must find the 32-byte M that encodes to it.

The model:

  • context = prev_byte * 256 + node (node = 1 then 2*node+bit)
  • 8 bits per byte, MSB first
  • prob init 0x800, total 0x1000, shift 12
  • bit 0: p += (0x1000 - p) >> 4 ; bit 1: p -= p >> 5
  • normalize while range < 1<<24

#4. Inversion

Because the encoder is deterministic, the inverse is the matching range DECODER run over the 36-byte target. It consumes exactly the bytes the encoder produced (verified: 36 in, 36 consumed) and yields the 32 diff-bytes D. Un-diffing (prefix XOR) gives M.

Two gotchas that cost time:

  1. The un-diff is a prefix XOR, not D[i]^D[i-1]. Since D[i] = M[i]^M[i-1], we have M[i] = D[0]^…^D[i]. Using D[i]^D[i-1] produces garbage.
  2. Validate by re-encoding. The decoder output alone isn't proof; feeding M back through the encoder must reproduce the 36-byte target byte for byte. It does (MATCH: True).

#6. Why it's "the-press"

The name is a hint at compression (a printing press "compresses" type onto a page). The %d/0x20 constant and the leading/trailing zero bytes were the breadcrumbs: 32 in, 36 out, LZMA-style flush → range coder → invert it.
