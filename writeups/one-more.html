This is textbook blind-Schnorr one-more unforgeability. The service even tells you the deal: "one signature per session, no exceptions - come back with more than that."

#2. Why the "obvious" attack is a trap

The classical break is Wagner's (ℓ+1)-sum / k-tree attack on the ROS problem. It works, but for a 256-bit curve it costs on the order of 2³⁴ hash evaluations and tens of GB of RAM for the k-tree. Two earlier sessions on this box burned all their time trying to shoehorn that k-tree (≈ 29 - 59 GB working set) onto a 16 GB machine with NVMe swap. That memory wall was the whole blocker.

Wagner is the generic algorithm for ROS. But ROS is not generically hard when the attacker controls the dimension: if you can open ℓ ≈ log₂(n) concurrent sessions, there is a polynomial-time solver (Benhamouda et al. 2021). secp256k1's order is 256 bits and the service allows up to 512 sessions - so ℓ = 256 sessions is plenty, and the whole thing becomes deterministic linear algebra. That is the intended solution.

#3.2 The forgeries

Use ℓ singletons plus one aggregate:

  • Singleton j (a = e_j): nonce R_j, message m_j. By (★) it is valid iff c_j ≡ H(R_j, m_j). So whatever message we settle on for session j forces the challenge we must send: c_j = H(R_j, m_j).

  • Aggregate (a = ρ, a vector we design): nonce R* = Σ_j ρ_j R_j, message m*. Valid iff Σ_j ρ_j c_j ≡ H(R*, m*).

The trick is to give each session two candidate messages, so each c_j has two possible values, and to engineer ρ so those binary choices add up to any target we need - with no search.

#3.4 Assembling the win

Sign each session once with c_j = h_j^{bit_j} → get s_j. Then:

  • 256 singletons: (m_j^{bit_j}, R_j, s_j) - each valid by construction.
  • 1 aggregate: (m*, R*, s* = Σ_j ρ_j s_j) - valid because we forced Σ ρ_j c_j ≡ T.

All 257 messages are distinct (encode j and the bit in each m_j; m* is its own tag). Result: good = 257 > answered = 256 → "one more!"

Resource budget: 256 open + 256 sign + submit + json = 514 commands ≤ 1088; 257 signatures ≤ 600. Comfortable.

#6. Takeaways

  • ROS is only hard generically. With ℓ ≥ log₂ n concurrent sessions the Benhamouda et al. solver is polynomial - Wagner's k-tree is a huge overkill that this challenge dangles to waste your time and RAM.
  • The gadget: per-session binary message choice + coefficient ρ_j = 2^j · d_j^{-1} turns each session into an independent power-of-two bit, so the aggregate equation is solved by just reading off the binary expansion of (T − L0) mod n. No search.
  • Blind Schnorr is broken in the concurrent setting; real deployments need ROS-resistant variants (e.g. Fuchsbauer - Wolf clause-Schnorr).
  • Practically: when a "known hard" attack needs 32 GB and 2³⁴ work for a 256-bit CTF that resets keys per connection and invites hundreds of sessions, that's a tell to look for the polynomial concurrent attack instead.

Reference: Benhamouda, Lepoint, Loss, Orrù, Raykova - On the (in)security of ROS, Eurocrypt 2021 - https://eprint.iacr.org/2020/945
