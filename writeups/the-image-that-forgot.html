The Image That Forgot timeline normalisation and OCI resolution

forensics
flag isfcr{57cfd556fca281af64d920ef}

#Objective

Recover the incident token of the container instance that was serving dispatch-ac1af5608a at 2026-08-14T10:10:08.555+05:30, then derive the flag.

Three artefacts were provided:

File What it is
events.jsonl 27 deployment events (activate / restart / migrate / rollback) plus tag→digest moves
images.tar An OCI image layout: index.json, oci-layout, blobs/sha256/*
vault.json 4 AES-256-GCM keys + 203 notes (nonce, data). Each plaintext is a token.

Each note is AES-256-GCM under one of the vault keys, with

  • 12-byte nonce,
  • data = ciphertext ‖ 16-byte tag,
  • AAD = compact JSON [service_id, key_version, manifest_digest, event_id].

The flag is then a scrypt+AESGCM KDF over [event_id, manifest_digest, service_id, key_version, token].

#Step 1 - Normalise the timeline (the "forgot" trick)

Every event timestamp arrives in a different offset (Z, +05:30, +05:45, -03:30, +01:00, -07:00, -05:00, +09:00). Nothing can be compared until everything is converted to one instant.

Target: 2026-08-14T10:10:08.555+05:30 = 2026-08-14T04:40:08.555Z.

The last successful event that (re)started the instance before the target is the migrate deploy-9d1a1fd93d (04:36:41.756Z). The activate two minutes later (deploy-ac1c2df5f4) has "status": "failed", so it never replaced the instance. event_id = deploy-9d1a1fd93d.

#Step 2 - index digest vs. manifest digest

The ref values in the events (dispatch:stable, and the raw sha256:… refs) are multi-arch OCI index digests (application/vnd.oci.image.index.v1+json, 724 bytes). The digest the instance actually ran is the platform-specific manifest the index points at for the instance's platform.

Resolution chain for the target instance:

manifest_digest = sha256:154d6f1fa75464d02b6245a4e536f6efb187af4bf7266aff8ac9e2e21d4538f8.

#Step 3 - key_version

Walking the image layers (etc/service/key-version.json) exposes the key_version strings. They are opaque identifiers that the deployments carry (key-3de4b6b00b, key-e52be7cc57, key-90a623d0c2, …). The tuple's correct value is pinned cryptographically in Step 4 - it is key-e52be7cc57.

#The generalised shortcut used by solve.py

Rather than hand-resolve one tuple, the solver enumerates the whole space (manifest_digest ∈ every blob × key_version ∈ every string found in layers × event_id ∈ every dispatch event) × all notes. Every one of the 203 notes authenticates under exactly one tuple, so the note layer alone does not disambiguate. The flag KDF is the : only the single correct evidence tuple produces a valid AES-GCM tag on the flag blob. That oracle uniquely returned the tuple above - confirming the timeline reasoning of Steps 1 - 3.

#Pitfalls hit

  • Treating the event ref (multi-arch index) as the manifest - the platform sub-manifest is the real manifest_digest.
  • Assuming key_version is an integer index into vault.keys - it is an opaque key-XXXXXXXXXX string, and it is not simply the top layer's etc/service/key-version.json (that file also appears at decoy paths etc/service.bak/… and opt/<svc>/templates/…).
  • Comparing timestamps without normalising the 8 different UTC offsets.
  • Counting a "status":"failed" activate as "the instance that started".
